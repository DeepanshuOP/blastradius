\begin{abstract}
Continuous Integration (CI) services execute automated test suites to detect regressions introduced by pull requests. While industrial platforms at Meta and Google leverage predictive models and large-scale workload analyses, the research community lacks public, reproducible benchmarks linking pull-request modifications directly to individual failing tests. We present \textsc{BR-Bench}, an open dataset linking code changes to fault-revealing tests mined from GitHub Actions logs across Java and Python open-source repositories. A test is defined as fault-revealing if and only if it fails at the head commit, passes or is absent in the resolved base run, and does not exhibit flakiness across runs on the same commit. The strict benchmark split contains 762 pull-request instances, 4,168 fault-revealing labels, and 2,466 distinct tests across 37 repositories. We evaluate test-to-file binding against pinned commit trees, achieving 94.29\% (5,643/5,985) combined binding and 63.83\% (3,820/5,985) full-confidence fully qualified name binding. In an illustrative application evaluating predictive test selection proxies at $k=10$, historical failure frequency achieves a micro recall of 39.44\% (519/1,316) whereas all-partner co-change file mining achieves only 4.64\% (61/1,316). We provide complete extraction pipelines without language model dependencies, processed release tables, and offline reproduction via a single command.
\end{abstract}

\section{Introduction}

Modern software development relies on continuous integration (CI) workflows to catch defects before pull requests merge into shared branches. In CI pipelines, every code modification triggers test suites that consume substantial time and energy. Predicting which individual tests are likely to fail on a given pull-request diff would let teams run failure-prone tests first and conserve compute.

Prior research addresses neighboring questions rather than empirical test-failure prediction. Change impact analysis (CIA) predicts co-changed program entities using version-control history~\cite{borg2017supporting,huang2022change}, capturing editing coupling rather than defect propagation. Regression test selection (RTS) tools, such as Ekstazi~\cite{gligoric2015practical} and STARTS~\cite{legunsen2017starts}, compute safe over-approximations via dynamic file or static class dependencies. In contrast, industrial deployments at Meta~\cite{machalica2019predictive} and Google~\cite{memon2017taming} run on proprietary monorepos, leaving underlying failure datasets inaccessible to researchers.

Existing open benchmarks do not fill this void: RTPTorrent~\cite{mattis2020rtptorrent} targets Travis CI job-level prioritization for Java, while GHALogs~\cite{moriconi2025ghalogs} archives raw GitHub Actions logs without test-level extraction, source binding, or flake filtering.

To bridge this divide, we present \textsc{BR-Bench}, an open benchmark connecting pull-request file changes directly to the individual test cases that failed because of them. Mined from real GitHub Actions pipelines across 76 swept repositories, \textsc{BR-Bench} extracts structured test outcomes from Gradle, Maven, and pytest execution logs. We resolve base runs on repository histories, filter same-commit test flakiness, and bind test identifiers back to repository source paths.

\section{Data Source and Collection Method}

\begin{figure}[t]
\centering
\input{figs/pipeline.tikz}
\caption{The \textsc{BR-Bench} construction pipeline. Raw CI logs and metadata are harvested, parsed into canonical test identifiers, matched against resolved base runs, filtered for flakiness, bound to source trees, and emitted as Parquet tables.}
\label{fig:pipeline}
\end{figure}

The construction pipeline of \textsc{BR-Bench} consists of seven reproducible stages (Fig.~\ref{fig:pipeline}): repository selection, metadata harvesting, log parsing, identifier canonicalisation, base-run resolution, test-to-file binding, and release bundling.

\subsection{Repository Sampling and Harvesting}
We selected candidate repositories from the SEART GitHub platform~\cite{dabic2021sampling}. Starting from an export of 3,671 open-source repositories, we retained 2,646 repositories active on GitHub Actions with at least 100 workflow runs in the preceding 90 days. We identified 2,333 repositories executing test-intent workflows (excluding linting or deployment tasks). We sampled 300 repositories into a balanced evaluation frame across Java and Python. The funnel counts 76 swept repositories and 165,349 runs (\texttt{instances\_raw}); the harvest corpus has 77 repositories and 175,038 runs (\texttt{corpus\_stats.md}). For each workflow run, the harvester downloaded run metadata, job step statuses, check-run annotations, and raw textual execution logs via the GitHub REST API.

\subsection{Log Parsing and Test Identifier Normalisation}
Because GitHub Actions treats test execution as unstructured stdout and stderr streams, test verdicts must be parsed from job logs. We built deterministic line parsers for three major test runners: Maven Surefire/Failsafe, Gradle Test Runner, and pytest. The parsers extract test outcomes (pass, fail, error, skip) and execution durations without relying on external large language models (LLMs). Each parsed test is mapped to a canonical identifier (\texttt{src/parse/test\_ids.py}): for Java, the format is \texttt{fully.qualified.Class\#method}; for Python, the format is \texttt{path::name}. Bare class identifiers are disambiguated using package declarations recovered from logs where available.

\subsection{Base-Run Resolution and Fault Revelation}
A test failure at a pull request's head commit does not imply that the pull request caused the failure; the test may have been broken in the upstream base branch. To establish causality, every failed head run must be paired with an appropriate base run. For each pull-request run on head commit $H$ targeting base branch commit $B$, we search repository history for a workflow run on $B$ executing the identical workflow. If a run on $B$ exists and completed with conclusion \texttt{success}, we record an \texttt{exact\_green} resolution. If no run exists on $B$, we traverse ancestor commits along the default branch within a maximum distance of 10 commits. In total, base resolution records five mutually exclusive statuses: \texttt{exact}, \texttt{exact\_green}, \texttt{ancestor} (max distance 10), \texttt{branch\_prior}, and \texttt{no\_base}. Under Invariant~6, runs resolving to \texttt{no\_base} emit zero labels.

The benchmark defines three nested splits (\texttt{src/label/fault\_revealing.py}):
(1)~\texttt{all} contains every $(\text{run}, \text{test})$ head failure in workflow runs with a usable base and parsed head test output;
(2)~\texttt{relaxed} removes tests that also fail in the resolved base run ($T_{\text{head\_fail}} \setminus T_{\text{base\_fail}}$); and
(3)~\texttt{strict} equals relaxed minus same-SHA flips (46/4,214 labels removed, $1.09\%$) to prune non-deterministic flakiness ($T_{\text{flaky}}$), yielding 4,168 strict positive labels:
\begin{equation}
T_{\text{reveal}} = (T_{\text{head\_fail}} \setminus T_{\text{base\_fail}}) \setminus T_{\text{flaky}}.
\end{equation}

\subsection{Flakiness Filtering and Test-to-File Binding}
Flaky tests flip their status non-deterministically without code changes~\cite{bell2018deflaker}. We detect same-SHA flips across repeated workflow executions on the exact same commit hash. Across 11,557 evaluated (head SHA, workflow, test) groups, 62 instances (0.54\%) flipped, leading to the removal of 46 flaky labels from the relaxed set (1.09\% of 4,214 labels) to form the strict set.

To enable change impact analysis, canonical test identifiers must bind to physical test source files. We bind identifiers against pinned repository clones recorded in \texttt{docs/CLONE\_PINS.json} rather than volatile branch heads. Basename-only matches achieve 0.5 confidence, while fully qualified class names that match uniquely achieve 1.0 confidence.

\textsc{BR-Bench} is distributed in Apache Parquet format for typed schema enforcement and columnar efficiency, documented via a dataset datasheet~\cite{gebru2021datasheets}. Table~\ref{tab:schemas} details the schema across release tables. Published release v0.1~\cite{brbench_data} contains four tables: \texttt{instances} (165,349 rows), \texttt{outcomes} (12,766 rows), \texttt{cochange} (175,204 rows), and \texttt{failure\_messages} (3,490 rows).

Release v0.2 (built offline and validated against schema.json via validator T1.6a, to be deposited as an updated version of the same Zenodo record before conference submission) maintains identical row counts and table grains while providing richer analytical fields. In \texttt{instances}, \texttt{base\_run\_id} is populated for 7,061 resolved runs (null for unresolved runs), with \texttt{base\_status} tracking resolution mode across all 165,349 runs (152,768 \texttt{not\_attempted}, 5,520 \texttt{no\_base}, 4,245 \texttt{exact\_green}, 1,858 \texttt{exact}, 591 \texttt{ancestor}, 367 \texttt{branch\_prior}), and \texttt{base\_run\_distance} recorded for 6,025 runs (median 0, p90 2, p99 8, max 10). Workflow start times are stored as typed UTC \texttt{TIMESTAMP} values in \texttt{run\_started\_at}. Changeset metrics (\texttt{n\_files\_changed}, \texttt{n\_lines\_changed}, \texttt{touches\_test\_file}, \texttt{touches\_build\_config}, \texttt{touches\_ci\_config}, \texttt{is\_docs\_only}, and \texttt{changed\_files} file paths) are provided directly, set to null for the 17,364 runs lacking changeset diffs.

In \texttt{outcomes}, data is structured in a long grain by split (one row per instance $\times$ test $\times$ split, spanning 4,384 distinct pairs). Release v0.2 augments this table with bound source paths (\texttt{test\_file}, 96.5\% coverage), \texttt{label\_source}, \texttt{parser\_confidence}, \texttt{status\_head}, \texttt{n\_job\_rows} (>1 for 690 pairs), \texttt{binding\_status}, \texttt{binding\_confidence} (1.0 for FQCN, 0.5 for basename), \texttt{duration\_s} (57.1\% coverage), and \texttt{failure\_message\_hash} (48.2\% coverage), while removing the pandas index artifact (\texttt{\_\_index\_level\_0\_\_}).

To protect contributor privacy, all author usernames in \texttt{instances.parquet} are pseudonymised using HMAC-SHA256 keyed by an operator-held secret, truncated to 16 hex characters across 1,791 unique authors (\texttt{docs/DATASHEET.md} \S4). Failure messages were scanned for credentials; zero blocking secrets were identified, while 5 review samples were flagged for human verification.

\section{How the Data Has Been Used: RQ1 Example}

\begin{figure}[t]
\centering
\vspace{-4pt}
\resizebox{0.65\columnwidth}{!}{\input{figs/rq1_chart.tikz}}
\vspace{-6pt}
\caption{Micro recall at $k=10$ across test selection proxies evaluated on \textsc{BR-Bench} ($n=576$ identical instances, 1,316 positive labels).}
\label{fig:rq1}
\vspace{-6pt}
\end{figure}

To demonstrate how \textsc{BR-Bench} serves as an empirical benchmark, we evaluate an example research question (RQ1): \textit{How accurately do conventional change impact analysis proxies and historical baselines identify fault-revealing tests?}

\subsection{Experimental Setup and Leakage Audit}
We evaluate four test selection heuristics at budget $k=10$: (1)~\textit{Co-change (All)}: trailing 365-day co-change partners from Git commits; (2)~\textit{Co-change (Test Only)}: co-change restricted to conventional test paths (\texttt{src/test/}, \texttt{*Test.java}, \texttt{test\_*.py}); (3)~\textit{Changeset Baseline}: pull-request modified files; and (4)~\textit{Historical Frequency}: $k$ most frequently failing bound test files from strictly earlier runs (strict labels, counted once per $(\text{test}, \text{instance})$).
To prevent temporal data leakage, co-change history was mined strictly prior to each run's start timestamp. An audit revealed that naive static co-change ended after the instance run in 713/713 audited instances and touched a changed file in 640/713 instances, while an uncorrected historical baseline double-counted failures across splits (224,758 rows for 78,399 distinct labels). Enforcing per-instance trailing windows, symmetric lookups, and single-split counting eliminated all leakage violations (0/713 in co-change and 0/762 in historical frequency).

\subsection{Results}
All methods are evaluated on identical instances where co-change yields predictions ($n=576$; 1,316 positive test labels; 462 Java, 114 Python). As shown in Fig.~\ref{fig:rq1}, all-partner co-change achieves only 4.64\% micro recall (61/1,316; mean P/R/J: 0.011 / 0.051 / 0.010; median size 14). Restricting co-change to conventional test files improves micro recall to 7.67\% (101/1,316; mean P/R/J: 0.054 / 0.087 / 0.038; median size 4). Sensitivity testing with any path containing ``test'' yields identical recall (101/1,316, 7.67\%; mean P/R/J: 0.048 / 0.087 / 0.033; median size 6). The changeset baseline attains 17.02\% micro recall (224/1,316; mean P/R/J: 0.039 / 0.245 / 0.037; median size 9). In contrast, historical failure frequency achieves 39.44\% micro recall (519/1,316; mean P/R/J: 0.185 / 0.517 / 0.178; median size 10). Removing environment and timeout failure labels leaves this ordering unchanged. Thus, historical failure frequency markedly outperforms version-control co-change heuristics at identifying true regressions.

\section{Originality and Similar Datasets}
\textsc{BR-Bench} differs from existing benchmarks along four axes:
(1)~\textbf{RTPTorrent}~\cite{mattis2020rtptorrent} provides Travis CI outcomes for Java by build job rather than PR diffs; it targets prioritization, not change-to-test linking;
(2)~\textbf{GHALogs}~\cite{moriconi2025ghalogs} archives raw logs without extracting test-level outcomes, linking PR diffs, resolving bases, or filtering flakiness;
(3)~\textbf{Static/Dynamic RTS Tools} (Ekstazi~\cite{gligoric2015practical}, STARTS~\cite{legunsen2017starts}, Chianti~\cite{ren2004chianti}) compute safe reachability over-approximations, whereas \textsc{BR-Bench} captures empirical CI failures; and
(4)~\textbf{Industrial Studies} at Meta~\cite{machalica2019predictive} and Google~\cite{memon2017taming} deploy predictive selection on internal monorepos, whereas \textsc{BR-Bench} is open and public.

\section{Limitations and Threats}
We identify five key limitations:
\textit{1) Roadmap Gates}: Gate~1 ($\ge 5,000$ strict positives) was \textbf{not met}, reaching 4,168/5,000 labels (83.36\%) and 762/5,000 instances (15.24\%). Gate~1.5 ($\ge 70\%$ binding) was met on combined binding (94.29\%, 5,643/5,985) but \textbf{not met} at full-confidence FQCN resolution (63.83\%, 3,820/5,985).
\textit{2) Parser Evaluation}: Precision on fixture (46/46) and holdout v1 (30/30) reflects development tuning sets; blind holdout v5 was \textbf{not scored} without independent human annotation.
\textit{3) Observational Ground Truth}: Labels reflect observational CI runs rather than isolated reruns; environment failures (2.14\%) and timeouts (2.69\%) remain present.
\textit{4) 90-Day Retention Cliff}: Because GitHub Actions purges logs after 90 days, 33.21\% of failed runs (4,458/13,422) had expired at harvest across the 77-repo corpus (as of 2026-08-29); full reproduction relies on our archived raw store.
\textit{5) Repository Skew}: The strict split is dominated by Java (35 Java vs.\ 2 Python), with high volume from active projects (e.g., Apache Beam, Stirling-PDF).

\section{Future Research Questions and Improvements}
\textsc{BR-Bench} enables three key directions:
(1)~\textit{ML Test Selection}: training neural models on code diffs to predict regressions without execution overhead;
(2)~\textit{Independent Re-execution}: executing planned causal subsets in isolated containers to separate regressions from environmental flakes; and
(3)~\textit{Multi-Language Expansion}: extending coverage to JavaScript, TypeScript, and Go.

\section{Conclusion}
We presented \textsc{BR-Bench}, an open benchmark linking pull-request modifications to fault-revealing tests across Java and Python GitHub Actions pipelines. By resolving base runs, filtering flakiness, and binding tests to source files, \textsc{BR-Bench} provides reproducible ground truth for regression test selection and impact analysis. Our evaluation demonstrates that historical test failure frequency markedly outperforms conventional co-change proxies, establishing an empirical baseline for future predictive test selection research.
