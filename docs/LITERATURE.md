# Literature review (35 papers, five groups)

Reading notes for the BITE497J report. **Each description is a summary of the paper's headline contribution written from its title and abstract; verify against the PDF before citing. No BibTeX or DOIs are given here on purpose: the team writes `refs.bib` entries by hand from the papers themselves.** URLs are the ones supplied with the task.

Groups: A = test selection and prioritisation in CI, B = build outcome and culprit finding, C = flaky tests, D = CI logs and LLM failure analysis, E = LLM program repair and agents.

## Gap

Three issues recur across the groups:

1. **Labels do not say who broke the test.** Prioritisation and prediction work (group A, B) is scored on build or test outcomes in which a failure that was already there counts the same as one the change caused; flaky failures are mixed in as well. BR-Bench resolves a base run so a label is a failure the change introduced, and reports the strict, relaxed and all splits (RQ1).
2. **Failure analysis and repair are change-agnostic.** The log-and-repair systems (group D) and most program-repair agents (group E) start from the log or the issue, not from the diff that introduced the failure. The two-arm comparison in E3 (R1 log-only vs R2 change-aware, same model) isolates exactly that difference.
3. **The stages are evaluated separately.** Selection, flaky-test handling and repair each have their own benchmark and data. Nothing links a prediction, a triage decision and a verified fix on the same failures; BR-Bench provides the shared ground truth, with the seeded benchmark covering the repair stage where real failures are not re-executable.

**Thesis for the report.** *Change-awareness is the missing ingredient in CI intelligence.* The three clauses are tested by E1 (does change information improve test prediction beyond history?), E2 (does it tell a developer which failures are theirs?) and E3 (does it make an automated fix more likely to be right?). Each experiment is allowed to come out negative, and the results in `docs/RESULTS_2.md` are reported as they came out.
