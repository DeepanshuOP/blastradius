# Mining pitfalls in GitHub Actions CI data

Material for paper §V. These are properties of the substrate, not bugs in
BlastRadius. Anyone mining Actions for execution-grounded labels will hit them.

All counts are over the 12,581-instance resolution frame at corpus pin
`2026-08-29T14:13:00Z`, regenerated by `analysis/corpus_delta.py` and
`src/label/fault_revealing.py`.

---

## 1. A workflow's name tells you nothing about whether it ran tests

This is the pitfall we got wrong ourselves, in both directions, and it is the
one worth writing up.

**5,684 of 12,581 instances (45.2%)** have a head run that parsed to
NO_TEST_OUTPUT — the run executed, concluded, and never ran a test. They are now
excluded by an inclusion criterion rather than labelled.

The ten most common workflow names among them:

| Workflow name | Instances removed |
|---|---:|
| PR Check | 320 |
| Validation | 222 |
| ci | 205 |
| Yetus JDK17 Hadoop3 Unit Check | 191 |
| Docs | 188 |
| Build | 173 |
| Java CI with Gradle | 166 |
| frontend | 162 |
| PR Lint | 147 |
| Clang format linter | 145 |

**Six of the top ten have test-suggesting names.** `Java CI with Gradle`,
`PR Check`, `Validation`, `ci`, `Build` and — most pointedly — `Yetus JDK17
Hadoop3 Unit Check`, which contains the words "Unit Check" and ran no parseable
test output at all. (For Yetus repositories the cause is known and separate:
they upload results as artifacts rather than printing them, and D-28 measured
artifact retention at 1–7 days, so those labels are permanently unrecoverable.)

**And it fails in the other direction too.** We initially classified `CodeQL`
and `CodeQL Advanced` (203 instances) as "visibly test-free" on the strength of
their names. Eleven of them survived into the strict split, and inspection shows
why: CodeQL's Java analysis **builds the project**, and a Gradle or Maven build
runs the test suite. Their extracted identifiers are ordinary, well-formed Java
tests —

```
org.fife.ui.rsyntaxtextarea.HtmlUtilTest#testGetTextAsHtml_happyPath
com.thealgorithms.datastructures.caches.FIFOCacheTest#testEvictionListenerExceptionDoesNotCrash
com.webauthn4j.data.attestation.authenticator.EC2COSEKeyTest#json_serialize_deserialize_test
```

— not parser noise. Those 11 instances are legitimate corpus members that a
name-based filter would have silently deleted.

**Consequence for anyone replicating this:** the only reliable signal that a run
executed tests is *parsing its logs and finding test output*. Workflow name,
workflow file path, and job name are all unreliable, and filtering on them
corrupts the corpus in whichever direction the mistake happens to fall.

## 2. A run conclusion is metadata about the run, not evidence about its tests

`conclusion == "success"` was, until Phase 017, taken as proof that a base run
was green — that `T_base_fail = ∅`. It is not. A run that executes a linter and
no tests concludes `success`.

Measured over the base runs verified so far, **346 of 762 instances (45.4%)**
whose base "succeeded" had a base that ran **zero tests**, confirmed by reading
every job log of the run. Treating those as green bases licenses every failing
head test to become a fault-revealing label against a base that never exercised
it.

The corresponding rule, now enforced in `BaseResolution.__post_init__`: a base
is green only if its logs were read and tests were observed to run without
failing. Everything else emits nothing.

## 3. Job metadata is permanent; job logs expire at 90 days

These two endpoints have different retention, and conflating them costs you the
ability to distinguish "we know" from "we cannot know".

- `GET /actions/runs/{id}/jobs` — succeeds indefinitely.
- `GET /actions/jobs/{id}/logs` — **410 Gone** after 90 days.

So an expired run can still be fully *enumerated* — you can know exactly how
many jobs it had and what each was called — while being permanently
*unreadable*. That asymmetry is why BR-Bench publishes `base_jobs_total` and
`base_jobs_retrieved` as columns rather than a footnote: the gap between them is
the share of the corpus that no future work can ever verify, by anyone.

It also produces a bucket that a naive design collapses: a matrix run where some
legs are retrievable and some have expired. If the retrievable legs show no
tests, that run is *indistinguishable* from one whose tests lived in the expired
leg. BR-Bench reports **CONFIRMED test-free** and **UNVERIFIABLE** separately and
never sums them, because they demote alike but are different epistemic claims.

---

## 4. Only failed jobs are worth fetching — on the head side, and only there

The head side legitimately filters to jobs that failed: that is where failing
tests are. Applying the same filter to the **base** side is a silent
catastrophe, because a green base run has no failed job by definition, so the
filter fetches nothing and NO_TEST_OUTPUT becomes the guaranteed verdict.

Measured cost of that bug in this project: **211 of 762 verified instances
(27.7%)** would have been wrongly demoted. All 220 verified base runs contain
zero jobs with `conclusion == "failure"`.

---

## 5. Matrix builds paginate

`/actions/runs/{id}/jobs` defaults to 30 per page and caps at 100. A matrix
build with more than 100 legs silently truncates unless you follow pagination to
`total_count` — and a truncated job set produces a *plausible* verdict rather
than an error, which is the worst failure mode available.
