## 2. What the project claims, and what it does not

**Claim (D-02).** Public benchmarks score change-impact analysis against **co-change** (files edited together) and regression test selection against **static reachability**. Neither records whether a test failed. Industrial predictive test selection (Meta, Google) uses the right label, but on private data. BR-Bench puts that label on public data, and measures how far co-change sits from it.

**A test is fault-revealing for a change if:**
- it failed at the head commit,
- it did not fail in the resolved base run, and
- it did not flip on the same commit (flaky).

**An empty base failure set is never read as "base was green":** `status = no_base` means no labels (ROADMAP §21.3). This applied to 5,520 of 12,581 failed runs.

**Not claimed / not built:**
- no safe-RTS guarantee (§17.1)
- no novel predictor; RQ2/RQ3 and the learned model were not reached
- no TypeScript (D-03)
- no cross-repo analysis (§44)
- no LLM in the reproducible core (D-17)
- no merge blocking

A negative model result is publishable (ROADMAP §37.1 Gate 3). **Never let an edit (from the guide or anyone else) re-frame this as a state-of-the-art predictor.** If the guide asks for that, say plainly what the data supports. §16.3 has the wording.

### 3.1 Rules that are always on (CLAUDE.md, Project instructions, user's standing instructions)

3. **Schema first, code second.** `docs/SCHEMAS.md` is frozen; a change is an escalation (D-54 is the precedent).
4. **Real fixtures, never mocks.** If a fixture test fails, fix the code, not the expected values.
5. **No new dependency without asking.**
6. **Determinism:** seed everything, pin everything.
7. **One task, one file (or one tightly coupled pair).**
8. **`test_id` is the frozen join key.** If a change would alter `test_id` output for an existing input, stop and flag it.

| Agent | Input → output | How |
|---|---|---|
| **Impact Analysis** | user story + codebase → `impact.json` + markdown | Keyword match of story terms to files/symbols, then **reverse reachability** in the code graph to tests. |
| **Coding** | impact + codebase → branch + PR | LLM patch, or `--patch` recorded JSON offline |
| **PR Reviewer** | PR + impact → review; merges; **returns commit id** | Scope check (strict/warn), compile check, tests-at-risk run; `--no-merge` |
| **Build & Deploy** | commit id + branch → build, package (`git archive`), deploy (`releases/<sha>`, `CURRENT`); **notify on failure** | Auto-detects pytest / `mvn package` / `./gradlew build`; refuses commits not on the branch; GitHub mode dispatches a workflow and polls |
| **Regression Suite** | impact + suite → test report | Runs selected scope (file-level for Python) and optionally `--full`; reports **impact recall** and missed failures; appends `history/test_outcomes.jsonl`, which the next impact analysis uses as failure history |

**Impact Analysis agent details:**
- Reverse-reachability edges: calls, imports, imports_from, uses, method, tests, tests_by_convention, tests_by_layout, inherits, extends, implements, plus `contains` reversed (symbol → file).
- **Risk score per test:** 0.55 × graph proximity + 0.15 × story-term match in the test name + 0.3 × past failure rate.
- **Risk level** (fixed in 6956f34):
  - **high** if change + dependent files ≥ 5, or there are gaps, or ≥ 50% of tests are reached;
  - **low** if ≤ 1 change file, 0 dependents and < 20% of tests reached;
  - otherwise **medium**.

**CLI:** `python -m src.agents {impact|code|review|deploy|regress|pipeline|demo}`.
- Common flags: `--repo`, `--state-dir` (default `<repo>/.blastradius`), `--provider offline|anthropic`, `--forge local|github`.
- `impact`: `--story/--story-file/--title`
- `code`: `--impact --patch --branch`
- `review`: `--impact --pr N [--no-merge] [--scope-policy strict|warn]`
- `deploy`: `--commit --branch [--build-cmd --deploy-dir --github-workflow]`
- `regress`: `--impact [--commit --full --runner-cmd --junit-glob]`
- `demo`: `[--workdir --export demo-web/public/data/agents.json]`

**Env vars:**

## 17. Viva / review Q&A (short answers)

**Q1. "You give the model the base and head commits, but the head is already committed and CI runs anyway. What's the point?"**
- The dataset uses **historical** commits because we need **ground truth**: what actually failed. That only exists after CI ran.
- In use, the prediction is made **before or while CI runs**, on the PR diff. Its value:
  1. **Order tests** so the likely failures run first (faster feedback).
  2. **Select a subset** for quick pre-merge or local runs; the full suite still runs later (no safety claim).
  3. **Review aid:** tell the reviewer which tests and areas are at risk.
- And the core contribution isn't the predictor. It is showing that the proxies used to **evaluate** such predictors (co-change, reachability) are far from real failures (co-change recall 4.64% vs failure history 39.44%). Anyone building a predictor needs BR-Bench to measure it honestly.
- The agents show this flow: the impact analysis runs on the **story, before code exists**.

**Q2. "Why not just use code coverage?"** Coverage needs instrumented runs at every commit, the cost that makes dynamic RTS impractical at scale (U11). We use real CI outcomes instead.

**Q3. "Why is Gate 1 not met?"**
- Attrition: only 6,586 of 12,581 failed runs had logs, 43.88% of failed runs had no base, and log expiry is 90 days.
- We chose not to relax the label definition. Precision over count.

**Q4. "What is binding and why two numbers?"**
- Binding maps a failing test id to its test file at the pinned commit.
- Combined (94.29%) includes lower-confidence tiers; full confidence is 63.83%. Reporting one alone would mislead (D-47).

**Q5. "How do you handle flaky tests?"** Same-commit flips (62/11,557 = 0.54%) are removed from the strict split.

**Q6. "Where is the AI?"**
- The reproducible pipeline is deterministic, with no LLM (D-17), so every number regenerates.
- The agents can use an LLM (Claude via API) but are a separate demo path (D-55).
- The graph is static analysis (tree-sitter via Graphify).

**Q7. "Is this already done by someone?"**
- Industrial predictive test selection (Meta, Google) uses private data.
- Public benchmarks use co-change or reachability labels.
- The closest-work matrix (slide 6, report ch. 2) shows the gap: public + execution-grounded + per-test.

**Q8. "How do I know the numbers are real?"** `make tables` regenerates every number offline, and each file is stamped with the script and git sha. The test suite has 824 tests on real fixtures. The data is on Zenodo with a DOI.

**Q9. "What did each member do?"** Deepanshu: harvester, labelling, ML/measurement, critical path. Sanskriti: parsers, measurement. Prisha: graph layer, tool. Confirm the exact split with the team before stating it.
