## 4. STAGE 4 DESIGN CONSTRAINTS

1. **Zero New Discovery Requests**: The Stage 4 work queue must be constructed entirely by reading already-persisted `jobs` records from `data/raw/{owner}__{repo}/run/{shard}/{unit}/jobs.jsonl.gz`.
2. **Prioritization Order**: The queue must sort failed-run jobs before successful-run jobs, and within each failure partition, sort by oldest run age first (`(0 if is_failed else 1, -run_age)`).
3. **Cross-Repo Queue Construction**: Like Stage 3 (`capture_checkruns`), Stage 4 queue construction and sorting must span across all repositories before entering the fetch loop.
4. **Single-Process Execution**: Stage 4 must run within the existing single-writer daemon architecture (or sequentially when PID 3053 is inactive), never as a concurrent second writer against `cursor.db`.
5. **Pre-Existing Vocabulary**: Stage 4 must use the existing `"logs"` kind, which is already registered in `rawstore.py` (scope `"job"`, int key `job_id`) and `cursor.py` (`_PARENT_RUN_SCOPES`).
6. **Parent Run Attribution**: When invoking `_fetch_job_log()`, Stage 4 must supply `parent_run_id=run_id` extracted from the job record to maintain run-level expiry attribution in `capture_unit`.
7. **Payload Size Reporting**: Stage 4 must aggregate downloaded log sizes from `_fetch_job_log`'s returned `bytes_fetched` integer, without loading whole log strings into memory.
8. **Expiry Tracking**: Stage 4 must track 404/410 responses as expired logs in its summary counters while treating other terminal/transient codes through the standard governor.
9. **CLI & Flag Integration**: `--stage` in `parse_args()` must support `"4"` (and include Stage 4 under `"all"` or an explicit multi-stage selection).
10. **Transient Governor Reuse**: Stage 4 must pass the shared `TransientGovernor` instance to regulate rate limits and transient errors across the global fetch loop.
