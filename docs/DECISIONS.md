| **D-19** | Raw-capture path keying | **`rawstore.path_for(repo, kind, key)` derives an explicit scope per kind from a `KIND_SCOPE` table (`page`/`pr`/`sha`/`run`/`checkrun`/`job`) instead of accepting one bare `run_id` for every kind, and instead of §8.3's originally-sketched `{owner}__{repo}/{yyyy-mm}/{kind}.jsonl.gz` monthly path.** The monthly path shares one file across every run in a month, which conflicts with cursor.py's contract that redoing an `in_flight` run must overwrite safely — a shared monthly file makes "redo one run" cost a full-month rewrite and risks crash damage to unrelated runs' data sharing that file. The single-`run_id` scheme it replaced had the opposite problem: PR numbers, commit shas, run ids, check-run ids, and job ids are five unrelated key spaces forced through one integer field, so e.g. PR #1234's `pull_files` and workflow run #1234's `jobs` landed in the same shard/unit directory with nothing in the path distinguishing them. The scope model makes a kind/scope mismatch unrepresentable (caller never passes scope) and each scope enforces its own key type (int, or 40-char lowercase-hex sha) | two-way | A kind needs a compound key a single scalar `key` can't express (e.g. `(run_id, attempt)` for re-run artifacts), or §8.3's endpoint set changes what each kind is looked up by |
| **D-20** | Cursor completion tracking | **(a) `capture_unit` (one row per `(repo, kind, unit_key)`, the same triple D-19's `rawstore.path_for` uses) replaces `run_capture` entirely.** Per-kind columns bolted onto `run_capture` were rejected: a run row only has a key for the two kinds it actually owns by `run_id` (`jobs`, `artifacts`) — `pull_files`/`pull_commits` have no run identity to hang a column off at all (G3), and a commit sha shared by two PRs can't be a per-run column either, since it isn't owned by any one run (G4). One table keyed exactly like rawstore's own addressing turns both gaps into "just more rows," and turns "is this run complete" into a query over real per-unit terminal status instead of a single flag that can drift from what actually landed (G1). Five terminal-adjacent statuses: `in_flight` (non-terminal) plus `complete`/`skipped`/`expired`/`failed`, added in that set now (not incrementally) because SQLite cannot `ALTER` a `CHECK` constraint in place — a status added after real rows exist costs a rebuild-and-copy migration, and `capture_unit` was still empty at the time this was decided. `logs`/`annotations` units also carry `parent_run_id` (NULL for every other kind) so the 90-day-expiring `logs` kind's expiry is attributable to the run the loop was iterating, which is what makes the §23.3 expiry rate a real per-run/per-repo number instead of a single pooled count. **(b) `repo_cursor` deliberately does not adopt §8.3 subtask 1's literal `repo, last_pr_updated_at, last_run_id, status` sketch** — it keeps `pr_page`/`sweep_status` instead, with no `last_run_id` and no bare `status` column. `last_run_id` has no real referent in the actual loop: PRs sweep linearly (`pr_page`/`last_pr_updated_at` is a genuine resumable pagination cursor over one endpoint), but runs are discovered per-PR, per-head-sha — there is no single "furthest run reached" watermark, and `newest_complete_run(repo)` computes the honest analogue on demand from real per-unit state instead of a column that could drift from it. A bare repo-level `status` would either duplicate `sweep_status` under a new name or try to compress potentially thousands of runs' state into one enum — reintroducing G1's exact bug one level up, at a coarser grain. Read §8.3 subtask 1 as a placeholder sketch predating the nine-endpoint fan-out design, not a column spec to reproduce literally. **(c)** `capture_unit.kind`'s `CHECK` constraint repeats rawstore.py's nine kind names as a SQL string literal, because a `CHECK` cannot reference `rawstore.ALLOWED_KINDS` directly — cursor.py validates `kind` against the imported `ALLOWED_KINDS` in Python at every call site and treats the `CHECK` as a backstop only, but the two listings are two places that must be kept in sync by hand | two-way | (a)/(b): a kind needs a compound key or an owning entity this model can't express. (c): if D-19's `KIND_SCOPE` ever gains or loses a kind and the `CHECK` in `_SCHEMA` isn't updated in the same change, capture_unit inserts for the new kind will raise `sqlite3.IntegrityError` instead of the intended Python `ValueError` — worth automating the sync (e.g. a contract test asserting the CHECK list matches `rawstore.ALLOWED_KINDS`) the next time this file is touched |
| **D-22** | Transient handling & dead credentials | **(a) A process-wide `TransientGovernor` pauses on a sticky 60/300/900s ladder, probing `GET /rate_limit` across every token at each rung, and aborts only after all three probes fail (1260s total); separately, a token returning 401 or producing `InvalidHeader` is evicted from the pool permanently for the life of the process, and `AllTokensDead` is raised when the last live token is evicted.** This supersedes aborting the run on the 5th consecutive transient failure with 401 treated as an ordinary transient. Measured on 40,324 logged requests: three historical aborts, all matching `MAX_ATTEMPTS x CONSECUTIVE_TRANSIENT_LIMIT = 30`, spanning 86s/386s/357s. Five units x six attempts x a 10s connect timeout is ~300s of blocked wall-clock on its own, so a 60-second wifi blip and a real outage produce identical signatures — "N consecutive within T seconds" cannot discriminate, whether the network returns can. Separately, 10 of 173 transients were 401s: with round-robin over three PATs a dead token fails at a 1-in-3 rate that never lands consecutively, so it trips no counter and silently costs a third of throughput. `InvalidHeader` x33 is the `.env` CRLF corruption surfacing, retried six times for nothing. **(b) Consequences.** (1) The governor is constructed once per process, not per repo — per-repo instances reset the sticky rung at every boundary, so a link flapping across a 300-repo sweep would never escalate past rung 1. (2) `AbortRun` is defined once, in `frame.py`. The duplicate in `daemon.py` meant `main()`'s handler could not catch what the governor raised — a live production regression. (3) The four `_fetch_*` helpers and the `_capture_pr` chain return `int \| None` status codes rather than the literal string `"transient"`. Without this the governor cannot see a 401 at all. (4) `AllTokensDead` deliberately bypasses the pause ladder. It is not a `RequestException`, so `_probe_all_tokens` does not catch it. This is intended: waiting cannot fix a dead credential, and pausing 21 minutes before failing is strictly worse than failing now. Do not "fix" this by adding a handler. (5) Eight broad `except Exception` sites (six in `daemon.py`, two in `process_repo`) carry a narrow `except AllTokensDead: raise` ahead of them. Verified non-destructive: `AllTokensDead` has no `.response`, so the `mark_unit_failed` branch is structurally unreachable and units stay `in_flight`. (6) Both entry points — `daemon.main()` and `frame.main()` — exit code 1 with an operator-legible stderr message rather than a traceback. **(c) Superseded tests.** `test_5_consecutive_transient_failures_abort_run`; `test_five_consecutive_transient_pr_failures_abort_run`; `test_main_all_tokens_dead_leaves_units_in_flight`'s five-PR expectation. Each renamed or rewritten with a docstring recording what it supersedes. One fixture in `test_frame.py` changed 401 to 503 — 401 was a generic stand-in written before eviction gave it meaning | two-way for the ladder constants; one-way in practice for eviction semantics, since a run that exited on `AllTokensDead` cannot be distinguished after the fact from one that never started | A token observed to recover after a 401 without any credential change — eviction is too aggressive. Ladder exhaustion firing on outages that later prove shorter than 21 minutes — ladder is too short. `InvalidHeader` recurring at all — the `.env` CRLF corruption has returned; fix the environment, not the handler |

(4) Stage 4 must copy stage 3's cross-repo oldest-first ordering, not the per-repo shape of stages 1-2. | **D-25** | Test identity two-key model | **Adopt a two-key model distinguishing canonical dataset `test_id` from internal `graph_node_id`, mapped deterministically via a one-way lossy derivation function.** (a) `test_id` is the canonical, lossless, case-preserving join key that ships in BR-Bench and appears in the paper (Java: `{package}.{Class}#{method}`; Python: `{path}::{Class}::{func}`, with casefold applied to the path component only). (b) `graph_node_id` is an internal, opaque, lossy key used solely to bind a test to a Graphify graph node. It is derived from `test_id` by applying Graphify's `normalize_id` recipe. One deterministic one-way function maps `test_id -> graph_node_id`; this mapping is many-to-one. **Technical basis and evidence:** Graphify's `ids.normalize_id` applies `NFKC`, then `casefold()`, then `NFKC` again, replaces every non-word character (`[^\w]+`) with an underscore, collapses repeated underscores, and strips leading/trailing underscores; `make_id` joins name parts with underscores. Under this transformation, `com.example.FooTest#testBar` becomes `com_example_footest_testbar`. Furthermore, Java method node IDs carry only the simple method name with no parameter signature (verified: `_JAVA_CONFIG` specifies no `resolve_function_name_fn`, so `_extract_generic` falls back to the tree-sitter `"name"` field). **Why not adopt Graphify's normalized ID as canonical `test_id`:** Casefolding an identifier merges `testBar` with `testbar` and `FooTest` with `Footest`. Java and Python are case-sensitive languages. In a relational join between harvest labels and code entities, an identifier collision does not raise an error — it manifests as a silent false-positive join, which is the worst failure mode available to this benchmark dataset. **Why not force Graphify to preserve case:** Graphify is vendored third-party code (`vendor/graphify-br/`) whose internal extractor, AST indexer, and query routines rely on `ids.py` normalization; mutating vendored third-party code risks breaking the internal consistency of the graphs it builds and diverging from upstream. **Consequences.** (1) D-09's instruction to make our IDs "consistent with graph node IDs" is satisfied by a deterministic derivation function (`graph_node_id = derive_node_id(test_id)`) rather than by literal string equality. A function `derive_node_id(test_id) -> str` must live in `src/parse/test_ids.py` alongside `normalize_test_id()`, applying Graphify's recipe, so there is exactly one implementation of the derivation in this codebase. (2) The many-to-one collision rate MUST be measured and reported as part of the Gate 1.5 binding analysis, not assumed to be negligible. (3) The published BR-Bench dataset carries canonical `test_id`; `graph_node_id` is an ephemeral internal binding key and need not be released. | two-way — changes internal binding derivation without altering canonical dataset schemas or raw harvest captures | Measured collision rate at Gate 1.5 exceeds 1% of bound tests, or any single graph_node_id binds two genuinely distinct test_ids within the same repository — derivation must change |

## The three that most often get violated silently

- **D-17** — someone adds "just one" LLM call for convenience. Any number touched by it is unpublishable.
- **D-09** — someone writes a second normalizer that is independently correct but disagrees on one Unicode edge case. Bindings drop silently.
- **D-05 / scope** — someone implements documented-but-deferred node types because Part IV describes them. Part IV is a spec, not a work order.

### D-34: Base resolution via commit graph and branch-run index
**Context**: We need to resolve base runs for PR failure instances. Keying on `run.pull_requests[].base.sha` was disqualified because it was only present on 10.27% of failed runs, and where both were present, it disagreed with `pr.base.sha` 45.20% of the time. (Measured: `uv run python patch3.py` in Phase 001).
**Decision**: Resolve base runs by walking the real commit graph from the blobless clone (`git rev-list --parents --all`), looking up ancestors in a branch-run index. 
- `base_ref` is used for branch queries because it is a branch name and does not move.
- We support an `exact_green` status: if the matched base run has `conclusion == "success"`, we resolve it but it yields an empty `T_base_fail`. This is NOT the invariant-6 trap because it is based on the *observation of a real run*.
- We cap the ancestor walk at a depth of 10 to limit unbounded resolution times.
- Logs that expired under the 90-day retention window result in HTTP 410s; these are an attrition number (T0.7) and not an error.

### D-35: run_attempt semantics
**Context**: 1,659 failed runs (13.19%) have `run_attempt > 1`, with a max of 28. (Measured via `cat << 'EOF' > /tmp/run_attempts.py ...`)
**Decision**: A label refers to the attempt explicitly captured in the raw API. The raw runs payload captures the specific attempt's status and conclusion.

### D-36: Transfer deadline and byte ceiling
**Context**: Log downloads can hang indefinitely if the connection stalls.
**Decision**: We enforce a wall-clock deadline of 29,704s and a byte ceiling of 15MB. The `p1 = 707 bytes/s` throughput floor across all files was derived using the command: `uv run python scratch/phase2b.py` (which read `requests.jsonl` durations and sizes).

## D-32 — Parameterisation

The canonical `test_id` is the SELECTABLE UNIT: the method, or for Spock the feature method. The iteration or parameter set lives in `TestId.params`, never in the canonical id. A pytest `[2-3-5]`, a JUnit `[1]` and a Spock `@Unroll` iteration are the same construct.

**Consequence:** for holdout_v3 fixture 15 (graphql-java), the hand label naming the feature template `#scenario` was CORRECT and the parser emitting the leaf iteration `directives on every schema kind` was wrong. This overturns the session-060 audit verdict on that fixture.

**Limitation (Accepted):** The canonical id casefolds the Python path component, which is lossy on a case-sensitive filesystem. Accepted because two Python test files in one repo differing only in case is close to nonexistent.

### D-37: Holdout corpus lifecycle
**Context**: A holdout corpus is scored exactly once. Any parser change informed by inspecting a corpus converts that corpus into a development set permanently, and its post-change score may never be reported as held-out performance. Superseding a held-out figure requires a NEW corpus under a new seed.

### D-38: Void versus superseded scoring
**Context**: A scoring event whose ground truth was produced by any automated extraction, including a grep or any function from this codebase, is VOID: no measurement occurred and the corpus is not consumed.
**Decision**: This is distinct from a superseded score under D-37, where a valid measurement was taken and later invalidated by a parser change. A voided corpus may be labelled again by hand and scored once.

### D-39: Java test identifier convention
**Context**: Disambiguating Java test identifiers across Surefire, Maven, and Gradle outputs when package prefixes are omitted in console lines.
**Decision**: (Architect ruling, verbatim):
"The canonical Java test_id is the fully-qualified class name, plus '::', plus the method name. The parser recovers the package from, in order: the surefire report header, the 'Running <FQCN>' line, any 'at' stack frame. If all three fail it emits the simple class name and sets fqcn_incomplete=True. It never infers or guesses a package."

### D-40: Language-ordered sweep
**Context**: `data/frame/frame_v1.csv` is block-ordered (all Java repos followed by all Python repos). Under sequential frame execution, Python repos were never reached while logs aged against the 90-day retention clock.
**Decision**: The harvester sweeps by language via `--lang` rather than in frame CSV order, because block-ordered CSV meant Python repos were never reached. Python log expiry at 90 days is irreversible, so Python is swept first.

### D-41: Artifact retention cadence
**Context**: Managing disk footprint, reproducible builds, and transfer requirements across local data tiers.
**Decision**: Explicit retention policy across data directories:
- `data/raw/` (4.6 GB): Irreplaceable. Retained permanently. Cannot be regenerated because GitHub Actions job logs expire at 90 days.
- `data/state/` (`cursor.db`, 131 MB): Irreplaceable cursor state required for `--as-of` reproduction. Retained permanently.
- `data/interim/` (~31 MB): Regenerable from `data/raw/` via pipeline scripts, but retained to avoid expensive re-parse runs.
- `data/clones/` (1.7 GB): Ephemeral blobless git clones. Regenerable on demand via `git clone --filter=blob:none`.
- `release/`: Staged/published release distribution artifacts (v0.1, etc.). Retained permanently for benchmark distribution.

### D-42: Schema conformance
**Context**: Reconciling on-disk Parquet datasets and release artifacts with frozen `docs/SCHEMAS.md`.
**Decision**: `SCHEMAS.md` is frozen and describes the full project scope including tables later cut. A column absent from disk is one of: CUT (its table is out of scope), DEFECT (fixable), NOT MEASURED (goes in datasheet limitations verbatim), RENAMED, or RESTRUCTURED. `SCHEMAS.md` is never edited to match what was built. No release ships with an unresolved DEFECT.

### D-43: Derivable negatives and candidate test universes
**Context**: Reconciling binary classification framing and negative test outcome generation with severe empirical class imbalance.
**Decision**: Negative examples are derivable, not materialised. BR-Bench ships positives plus candidates.parquet giving the full observed test set per repo per trailing window. Consumers derive negatives at any ratio. Rationale: materialising at the observed imbalance produces tens of millions of rows for 8,980 positives, and a frozen sampling ratio is a weaker artifact than the universe it was sampled from.

### D-44: Gate 1 reads against the label count, not the instance count
**Context**: ROADMAP §37.1 states Gate 1 as ">=5,000 positives." Phase 014-A reported this against the strict-split instance count (778), reading Gate 1 as MISSED at 778/5,000. ROADMAP §9.3 step 6 defines the labelling grain explicitly: one row is emitted per (instance, candidate test) pair, label 1 if the test is in T_reveal. A positive, under that definition, is a (change, test) pair — a label — not an instance.
**Decision** (Architect ruling, verbatim): "Gate 1's >=5,000 positives therefore reads against the label count, currently 4,194, not the instance count of 778. Gate 1 stands at 4,194/5,000, not met."

### D-45: Secret-scan severity tiering
**Context**: `analysis/secret_scan.py` (promoted from the throwaway `tmp_scan.py` that produced the Phase 009-B result) is a T1.6b release blocker wired into `make tables`. Its four patterns are inherited byte-identical from 009-B. Run against `release/v0.1`, two of them fire only on harvested public data: all six `internal_host` matches are public identifiers (`jdk.internal`, `org.knowm.xchart.internal`, `Dockerfile.local`, `ConnectDialog.internal`, `heuristicEngine.corp`, `org.jkiss.dbeaver.app.local`) and all 25 `email` matches are Apple asset filenames of the form `AppIcon-20x20@2x.png`. Gating a release on either would fail every build on noise, which is how a blocker stops being read.
**Decision**: Findings carry two severities. **BLOCKER** — `github_token`, `bearer_token` — fails `make tables` with a non-zero exit; neither shape can occur in harvested public source. **REVIEW** — `email`, `internal_host` — is printed for human triage and is never fatal. The patterns themselves are not weakened, only their consequence: a real `.corp` host is still reported, it just is not the thing that stops the build. Matched text is never printed in full; every sample is redacted to its first three characters plus its length, so running the scan cannot itself leak a credential into a log, a report, or the paper.
**Revisit trigger**: a credential class appears that is not `gh[pousr]_`- or `Bearer`-shaped, or a release ships a host we control.

### D-46: Class-level failure events are not test ids, and are counted rather than dropped silently

D-46 — Class-level failure events are not test ids, and are counted rather than dropped
silently. A CI failure that names a class with no source-level method — a Maven class-level
`<<< ERROR!` line, or JUnit4's synthetic `classMethod` descriptor for a @BeforeClass /
@AfterClass failure — describes a fixture or suite failure, not a test. Emitting it as
<class>#<method> manufactures an identifier that names no source symbol, can never bind, and
fragments the join key. Such events MUST NOT be emitted as a test_id. They MUST be counted
and the count reported on every parse run; silent deletion is forbidden, because the
brooklin `Gradle suite` defect showed that a discarded outcome leaves no trace and is
therefore undetectable. Distinguishing rule: a method-position token is legitimate if it
names a developer-written source symbol (setup, init, run, TestAll all do); it is not
legitimate if the test framework synthesised it (classMethod does not). Revisit trigger: a
framework is added whose synthetic descriptors are not enumerable.
